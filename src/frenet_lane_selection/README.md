# Frenet 차선 선택 로직

**ROS 없는 C++14 알고리즘 라이브러리. 통합 전 합성 검증 단계이며 실차 주행 승인이 아니다.**
노드, launch, 센서 드라이버, 검출기 전체, 카메라 인식기, 제어기, 지도 파일은 포함하지 않는다.
기본 Frenet 라이브러리와도 빌드 의존성이 없다. `catkin_make`로 자동 실행되는 패키지가 아니다.

## 역할과 경계

`selectLane(observation, permission, context, config)`는 **현재 활성 경로 구간에 투영된
2D LiDAR 표면 관측**에서 양쪽 도로 경계 후보를 찾고, 외부에서 허용한 목표 차선을 반환한다.
`valid=true`는 경계 후보와 차선 목표를 계산했다는 뜻일 뿐, 차선 변경 경로가 충돌 없이
주행 가능하다는 뜻이 아니다. 반환된 `target_x/y`를 `/path/final`로 곧바로 발행하면 안 된다.

분류기는 아니다. 벽/차량 옆면이 연석과 동일한 형상으로 보이면 2D 기하만으로 구별할 수 없다.
20 cm 연석 높이는 관측 라벨로 사용하지 않는다. 스캔 평면이 연석에 실제로 닿아야 한다.
과거 기울어진 마운트의 bag을 수평 장착 검증 결과로 간주하지 않았다.

## 입력

- `Observation.sections`: 진행 순서의 단면들. 각 단면은 고정된 동일 좌표계의 RDDF
  `s`, 위치, 접선 yaw 및 그 단면 근방에서 관측된 점들의 횡방향 거리 `d`를 가진다.
  **왼쪽 + / 오른쪽 −, m / rad**다. 단면 길이 방향의 bin 폭은 통합자가 명시해야 하며,
  그 안에서 경계 변화가 설정된 오차보다 크지 않아야 한다. 서로 다른 구간의 점을 섞지 않는다.
- TF, 뒤집힌 장착 보정, 스캔 deskew, 측정 시각/순서 검사, ROI/가림 검사, 유효 점의 중복
  제거, S자·평행 구간의 제한된 `s` 투영은 입력 어댑터 책임이다. 이 조건 확인 후에만
  `input_contract_valid=true`를 전달한다. 이 bool 자체는 검증을 대신하지 않는다.
- `Permission`: 외부 미션/화살표·X 판정 결과의 유효성·나이, 좌우 허용 여부, 선택 요청.
  연석이나 가까운 거리에서 주행 허가를 추론하지 않는다. `requested=Unknown`이면
  한쪽만 허용된 경우 그쪽, 둘 다 허용된 경우 현재 차선을 유지한다. 현재 차선도 모호하면 실패한다.
- `SelectionContext.current_offset_m`: **첫 단면에 대응하는** 차량의 횡방향 위치.
  멀리 떨어진 단면에 현재 차량의 d를 그대로 복사하면 안 된다. `current_lane`은 선택적이다.
- `age_sec`: 측정 후 경과 시간. 통합자는 원래 stamp 및 monotonic receipt-age 둘 다 검사하고,
  rosbag/ROS clock 정지 중에도 이 나이가 증가하도록 해야 한다. 오래된 입력을 재포장하지 않는다.

전역 경로·스캔 좌표계 변환을 라이브러리가 다시 수행하지 않으므로 TF 중복 적용이 없다.
현재 검출기의 `ObjectInfo` AABB만으로는 이 단면별 원시 표면 점을 복구할 수 없다.
검증된 LiDAR 점을 별도 어댑터로 입력하고, 기존 장애물 관측은 충돌 검사에 그대로 남겨야 한다.

## 경계 후보와 차선 결정

각 단면에서 d를 정렬·군집화한 뒤, 양쪽 표면의 **안쪽 면** 간 폭이 기본 `6.54 ± 0.30 m`인
유일한 조합만 채택한다. 여러 조합이 가능하면 더 넓거나 가까운 조합을 임의로 고르지 않는다.
모든 단면에 양쪽 관측이 있어야 하고, 기본 최소 6단면·3 m 길이, 최대 단면 간격 1 m,
경계 변화율 및 기준선 위치·접선 연속성 검사를 통과해야 한다.
이 수치는 개발 초기값이며 실제 센서 오차·구간 폭의 검증값이 아니다.

관측된 왼쪽 경계를 `dL`, 오른쪽을 `dR`라 하면:

```text
도로 중앙 = (dL + dR) / 2
왼쪽 차선 중앙 = (3*dL + dR) / 4
오른쪽 차선 중앙 = (dL + 3*dR) / 4
```

도로 중앙 RDDF와 정확히 6.54 m 폭인 경우에만 차선 중앙이 ±1.635 m가 된다.
예를 들어 RDDF가 한쪽으로 치우쳐 `dL=4.27`, `dR=-2.27`이면 목표는 `+2.635 / -0.635 m`다.
6.54 m는 양쪽 관측을 검사하는 prior이지, 안 보이는 연석을 만들어 내는 값이 아니다.
이는 두 개의 **동일 폭 차선**이라는 사용자 조건을 전제로 한다. 합류·교차로·가변 폭·비대칭
차선에서는 이 모델을 사용하지 않는다.

요청 차선이 금지됐거나 양쪽 금지, 허가/관측 stale, 한쪽 가림, 경계 조합 모호,
불연속·잘못된 숫자·계산량 상한 초과이면 `valid=false`, `lane=Unknown`, `targets=[]`다.
stateless 코어라 과거 차선 목표를 자동 재사용하지 않는다. 프레임 간 확인/히스테리시스는
통합자 책임이며, 무효 프레임에 이전 목표의 timestamp만 갱신하면 안 된다.

## 기본 Frenet과 연결 시 주의

이 결과는 `(s, target_d)` 목표와 양쪽 관측 경계다. 현재 기본 Frenet은 **입력 기준선 d=0**으로
복귀하며 목표 차선 API가 없다. 따라서 두 라이브러리를 단순히 같이 실행한다고 차선 변경이
되지는 않는다. 통합자는 다음 중 하나를 별도 구현·검증해야 한다.

1. 검증된 차선 중심을 새 기준선으로 구성하고 기존 경계를 그 기준선에 다시 표현한다.
   현재 후륜축 pose에서 목표 기준선까지 연속적인 접속을 만들고 경로 변경 시 이전 경로 상태를 초기화한다.
2. Frenet 후보 생성/비용/종료 조건에 명시적 목표 d profile을 추가한다.

기존 lateral 탐색 범위는 ±1.50 m이므로 ±1.635 m조차 기본 설정의 정확한 목표로 지정할 수 없다.
한 차선 중심에서 다른 차선 중심까지는 약 3.27 m다. 탐색 폭만 키우는 것은 안전한 연결 구현이 아니다.
두 방식 모두 곡률·차체 회전/swept 충돌·최신 odom 관측·금지 차선 통과/정지선 조건을 재검사한다.
차선 목표점에 장애물이 있으면 이 코어는 피하지 않는다. 목표 차선의 차선 변경 허가와 그
경로가 실제로 비어 있는지는 서로 다른 조건이다. 자동 회피·주행 허가는 planner/mission 계층 소유다.

## ROS 없이 빌드·시험

이 폴더를 기준으로 (CMake 3.10+, C++14 컴파일러):

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j2
(cd build && ctest --output-on-failure -V)
```

합성 시험은 정상/치우친 기준선, 곡선 법선, 허용/금지, 동률, 한쪽 소실,
내부 장애물 표면, 복수 경계, 폭·연속성, stale/NaN/계산량 및 과거 목표 미재사용을 검사한다.
실제 연석 검출 정답률, 보행자 추적, 실제 차선 변경/제동은 검증하지 않았다.
